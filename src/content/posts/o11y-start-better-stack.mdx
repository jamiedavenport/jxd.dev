Modern web apps are distributed systems, even when they look simple on the surface. When a single user action fans out into server functions, database calls, and third‑party APIs, you need end‑to‑end visibility to understand where time is spent and why errors occur. That’s exactly what tracing provides.

In this post we’ll add tracing to a TanStack Start application using OpenTelemetry and export those traces to Better Stack via OTLP. We’ll keep the scope intentionally tight: this guide focuses only on tracing. No metrics, no logs—just high‑signal spans that tell the story of each request from start to finish.

# Instrumentation

To capture spans from your server and common libraries, you’ll install the OpenTelemetry Node SDK, the auto‑instrumentations bundle, and the OTLP HTTP trace exporter. This gives you a foundation of automatic spans (HTTP, fetch, database drivers where supported) plus the ability to create your own custom spans around important business logic.

```sh
bun add @opentelemetry/sdk-node @opentelemetry/api @opentelemetry/auto-instrumentations-node @opentelemetry/sdk-metrics @opentelemetry/sdk-trace-node
```

Next, create an `instrumentation.ts` file that initializes the OpenTelemetry SDK as early as possible. In this file you’ll:

- Declare service metadata (for example `service.name` and `deployment.environment`) so spans are grouped correctly in Better Stack.
- Configure the OTLP trace exporter with the endpoint and auth headers provided by Better Stack’s Traces Source.
- Enable Node auto-instrumentations so common libraries are traced out of the box.
- Start the SDK on boot and register a clean shutdown handler to flush spans on process exit.

```ts
// src/instrumentation.ts

import { NodeSDK } from "@opentelemetry/sdk-node";
import { ConsoleSpanExporter } from "@opentelemetry/sdk-trace-node";;

const sdk = new NodeSDK({
	serviceName: "big-journal",
	traceExporter: new ConsoleSpanExporter(), // Temporary
});

sdk.start();
```

With the SDK ready, ensure it runs before any application code that you care to trace. Import `instrumentation.ts` at the very top of your TanStack Start server entry so the tracer is active before routes and server functions load. In serverless or edge environments, make sure the import path and initialization happen exactly once per runtime instance.

```ts
// src/server.ts

import handler from "@tanstack/react-start/server-entry";

import "./instrumentation";

export default {
	fetch(request: Request) {
		return handler.fetch(request);
	},
};
```

Finally, add manual spans in your high‑value server functions. Use the active context to start child spans, set attributes like route ID, user ID (if appropriate), input sizes, and downstream dependency names, and record exceptions when things go wrong. These targeted spans complement the automatic ones and make investigations much faster in practice.

```ts
// src/routes/example.tsx

import { trace } from "@opentelemetry/api";
import { createFileRoute } from "@tanstack/react-router";
import { createServerFn } from "@tanstack/react-start";

const tracer = trace.getTracer("example");

const testFn = createServerFn({ method: "GET" }).handler(() => {
	return tracer.startActiveSpan("testFn", async (span) => {
		try {
			return "Hello World";
		} catch (error) {
			span.recordException(error);
			throw error;
		} finally {
			span.end();
		}
	});
});

export const Route = createFileRoute("/example")({
	component: RouteComponent,
	loader: () => ({
		data: testFn(),
	}),
});

function RouteComponent() {
	const { data } = Route.useLoaderData();
	
    return <div>{data}</div>;
}
```

# Better Stack

In Better Stack, create a Traces Source for your application. This will generate an OTLP HTTP endpoint and the necessary authentication details. Point your OpenTelemetry trace exporter at that endpoint and include the provided headers or token—this keeps the setup simple without needing a custom exporter.

Deploy your changes and exercise a traced route. Within moments you should see spans flowing into Better Stack. Use the traces view to:

- Filter by `service.name` and environment to isolate deployments.
- Expand a trace to see each span’s timing and attributes.
- Identify the slowest segments and drill into the exact server function or outbound call responsible.

```ts
import { OTLPTraceExporter } from "@opentelemetry/exporter-trace-otlp-proto";
import { NodeSDK } from "@opentelemetry/sdk-node";
import { env } from "./env";

const sdk = new NodeSDK({
	serviceName: "big-journal",
	traceExporter: new OTLPTraceExporter({
		url: env.BETTERSTACK_TRACE_URL,
		headers: {
			Authorization: `Bearer ${env.BETTERSTACK_SOURCE_TOKEN}`,
		},
	}),
});

sdk.start();
```

# Global Middleware

To get consistent, top‑level spans across every request, add a global tracing middleware. Create a span per incoming request, attach attributes such as HTTP method, path pattern/route ID, and response status, then end the span in a `finally` block so it always closes—even on errors. This establishes a clear parent span for any work done downstream, making entire traces easier to read.

## Server Function Names

Out of the box, server functions can appear with hashed or implementation‑derived names, which aren’t very helpful when skimming traces. You have two practical options:

- Start spans with descriptive names that reflect intent, like `users.create`, `billing.charge`, or `checkout.placeOrder`. You can also rename an active span to something clearer once inputs are known.
- Wrap server functions in a small helper that creates a span using a meaningful, fixed operation name, then runs the underlying logic within that span’s context.

Either approach ensures the Better Stack UI shows human‑readable operation names, making it faster to spot slow or failing parts of a request.
